# 代码重构（按重写的思路）

> 前置规则：先加载 [`ai-collaboration.md`](../../rules/ai-collaboration.md)，其「不保留向后兼容」「选最简实现」「优先成熟库降复杂度」等通用准则在重构中全部生效，本文不再复述，仅给重构专属的判据与流程。
> 语言细节：改动具体语言时加载 `languages/{js,python,go,cpp,swift,bash}.md`，其为该语言起步基线、旧→新惯用法映射、库选型与工具链的唯一权威。
> 工程治理（脚手架/发版/依赖/CI）属 `project-setup` skill，不在此列。

## 一句话判据

重构的成品，必须等同于「照着最终需求从零写一遍」的结果。有人来读，只能看出它天生如此，看不出任何从旧代码改过来的痕迹——这是每次收尾时的自检问题。

## 按四步推进

**第一步 · 画出终局。** 先不碰旧代码，把「最终应该长成什么样」定下来：数据模型、模块边界、对外接口、依赖清单。这份蓝图既是施工图，也是验收尺。同一步里顺带判断能否借三条路径把复杂度砍下去（三选多，能省则省；引依赖照 `languages/{lang}.md` 的选型判据）：

- 把手写的通用能力（参数解析、日期、校验、重试、限流、状态机……）换成成熟库，如 `zod`、`pydantic`、`typer`；
- 通用且与业务无关的能力，若无合适开源库可用，也不要散落在业务代码里：抽成独立子目录（含单独设计文档），对外只暴露清晰接口，让业务模块通过接口消费、完全不感知其内部实现——业务代码里只剩业务逻辑；
- 把自研脚本和散落配置收敛到标准工具链（格式化 / lint / 类型 / 测试 / 构建，具体见 `languages/{lang}.md`）；
- 若旧结构本身就错，换整套模型——合并重复、拆开巨型函数、压平嵌套、用数据表取代成堆分支，而非局部打补丁。

涉及新依赖或大结构调整，先与用户对齐再动手。

**第二步 · 铺好安全网。** 关键行为若无测试覆盖，先补上；测试只钉住「对外可观察行为」，不绑内部实现，以便证明重构前后一致。

**第三步 · 照蓝图重写，并顺手清空这些东西：**

- 演化痕迹——记录「当初为何这么改」的注释、注释掉的旧实现、`// deprecated`、`// 兼容老版本`。这些交给 git，不留在代码里。
- 兼容与回退——为过渡而生的版本判断、双写、feature flag、adapter/shim、`if 兼容 A else 兼容 B`。终局只有一条路径，其余删净。
- 孤儿残留——重构后再无人引用的 import、变量、函数、类型、常量、配置、依赖、测试、死分支。
- 旧名字——`handleV2`、`newXxx`、`tmpFix` 这类还背着历史语义的命名，一律改成描述其最终职责的名字。
- 旧 agent 说明文件——遇到 `CLAUDE.md` 一律迁移为跨工具中立的 `AGENTS.md`（内容原样迁移、同步更新内部引用与路径），不再保留 `CLAUDE.md`。

除清理外不夹带无关改动。

**第四步 · 验收交付。** 跑通「格式 → lint → 类型 → 测试」全绿，对着第一步的蓝图逐项核对：形态到位、行为未变、包袱清零。交付时讲清：终局是什么、清掉了哪些历史包袱与兼容逻辑、依赖有何增减、用哪些命令验证。

## 红线：只换形态，不改功能

「像重写」说的是代码长相，不是功能范围。除非用户点头，对外行为必须与重构前完全一致。途中若发现能顺手修的 bug 或想改的行为，先提出、经确认，绝不静默塞进这次重构。
